Here's the full technical audit of the NOVA codebase, covering only issues **not already listed in BUG.TXT**.---

## NOVA — Technical Audit Report (New Issues Only)

---

### 1. Bugs & Runtime Errors

---

**BUG-01 — `_commit_memory_async` has a TOCTOU race on `_memory_jobs_inflight`**
Severity: Major | Priority: High

```python
# main.py — no lock around this check+increment
if self._memory_jobs_inflight >= self._max_background_memory_jobs:
    return
self._memory_jobs_inflight += 1
self._memory_executor.submit(_job)
```

Two threads calling `ask_stream` concurrently can both read the same value of `_memory_jobs_inflight`, both pass the guard, and both submit, potentially exceeding `_max_background_memory_jobs`. The summary inflight counter uses `self._summary_submit_lock` correctly, but the memory inflight counter has no equivalent lock.

**Fix:** Wrap the check-and-increment for `_memory_jobs_inflight` inside a dedicated lock (reuse `_summary_submit_lock` or create `_memory_submit_lock`).

---

**BUG-02 — `GoalRunner._executor` can receive submissions after `close()` during shutdown**
Severity: Major | Priority: High

In `NOVAApp.shutdown()`:
```python
self._stop_autonomy_loop()   # joins thread with timeout=2s only
...
self.goal_runner.close()     # shuts down GoalRunner._executor
self.autonomy_runner.close()
```

`_stop_autonomy_loop()` joins with a 2-second timeout. If the autonomy thread is blocked on a long-running tool step (up to `GOAL_STEP_TIMEOUT_SECONDS = 60s`), it outlives the join. Then `goal_runner.close()` shuts down the executor, and when the autonomy thread's step finally finishes, its `_executor.submit()` call raises `RuntimeError: cannot schedule new futures after shutdown`.

**Fix:** Before closing executors, wait for the autonomy lock to drain: `self._autonomy_execution_lock.acquire(timeout=5)` after stopping the thread, or pass the `_shutting_down` event into `GoalRunner` and check it before submitting.

---

**BUG-03 — Off-by-one in `approved_for_step` cursor advancement**
Severity: Major | Priority: High

In `_autonomy_loop`:
```python
result = self.autonomy_runner.run(
    steps[start_index : start_index + 1],
    max_steps=1,
    start_index=0,
)
result.next_index = start_index + (1 if result.status == "completed" else 0)
```

If `start_index >= len(steps)`, `steps[start_index:start_index+1]` is an empty list. The runner completes instantly with `next_index=0`. Then the code sets `result.next_index = start_index + 1` (e.g. `len(steps) + 1`), writing an out-of-bounds cursor value to the persisted goal. The next poll of this goal finds `cursor > len(steps)` and the `GoalResult` immediately returns `completed` — but the goal record is left with a nonsensical cursor.

**Fix:** Guard with `if start_index >= len(steps): mark completed directly`. Also clamp the cursor to `min(result.next_index, len(steps))` before persisting.

---

**BUG-04 — Background summarization writes empty string to `trimmer.summaries`, poisoning context**
Severity: Major | Priority: Medium

`_summarize_history()` returns `""` until the background job populates the cache. `ContextTrimmer.trim()` receives this empty string, detects it's blank, and falls back to `snippet[:700]` — raw truncated turn text — which it then stores in `trimmer.summaries[session_id]`. On subsequent calls the trimmer sees a "summary" that is actually raw turn text. The background job later stores the real summary, overwriting it. But for all messages between the first overflow and the background completion, the context contains uncompressed turn data, inflating token counts and degrading response quality.

**Fix:** Don't store the fallback `snippet[:700]` in `trimmer.summaries`. In `trim()`, if `compressed` is empty, return `("", recent)` rather than storing the raw snippet as the summary. The background job will populate the real summary before it's needed.

---

**BUG-05 — `tray.py::on_health` inner retry is still an identical call**
Severity: Minor | Priority: Low

From BUG.TXT's BUG-NEW-03: the fix was acknowledged but looking at the current `tray.py`:
```python
def on_health(_icon, _item):
    try:
        _notify("NOVA Health", _format_health_summary(agent))
    except Exception as exc:
        _notify("NOVA Health", f"Health unavailable: {exc}")
```

The outer `try`/`except` is now clean. This item is now **resolved**. However the `_format_health_summary` function references `agent.health.status_table()` with no guard — if `agent.health` is `None` (partial construction failure), this raises `AttributeError` which is caught and reported generically. No actual bug remaining, just a fragile error message path.

**BUG-06 — `mark_rate_limited` reads `record.failures` outside the lock**
Severity: Minor | Priority: Low

```python
# core/llm/roundrobin.py
with self._lock:
    record.failures += 1
    ...

# OUTSIDE the lock:
get_logger(__name__).warning(
    f"Key {label} is rate-limited (failure #{record.failures}); ..."
)
```

After the `with` block releases the lock, another thread can increment `record.failures` before the log statement reads it. The log will show an incorrect (stale or future) failure count. Not a correctness issue in practice, but a misleading audit trail.

**Fix:** Capture `failure_count = record.failures` inside the `with` block and use it in the log.

### 2. Connectivity & Integration Issues

---

**CONN-01 — Telegram `_stream_text` silently swallows exceptions from `ask_stream`**
Severity: Major | Priority: High

```python
def _worker() -> None:
    try:
        for token in agent.ask_stream(prompt_text):
            token_queue.put(token)
    finally:
        token_queue.put(None)  # exits loop, buffer is empty
```

If `ask_stream` raises (e.g., `SettingsError`, unhandled `RuntimeError`), the `finally` block puts `None` and the main coroutine exits with `buffer = ""`, replacing the placeholder with `"(no output)"`. The user gets silent failure with no error context. The exception is completely lost.

**Fix:** Catch exceptions in `_worker`, put an error string token before the `None` sentinel, or store the exception and re-raise it after the await loop.

---

**CONN-02 — Telegram `on_export` has an unhandled `FileNotFoundError`**
Severity: Minor | Priority: Medium

```python
async def on_export(update, _context):
    ...
    path = agent.export_session("md")
    with open(path, "rb") as file_handle:  # raises FileNotFoundError if disk full
        await update.message.reply_document(...)
```

If the file write in `export_session` fails silently (disk full) and returns a path that doesn't exist, the `open()` call raises `FileNotFoundError`. This is unhandled in `on_export` and propagates to python-telegram-bot's default error handler, giving the user no feedback.

**Fix:** Wrap in `try/except` and reply with an error message.

---

**CONN-03 — `LocalMemoryStore._init_chroma()` is not thread-safe for concurrent reinit**
Severity: Major | Priority: Medium

```python
# In add(), called from multiple threads simultaneously
if not self._use_chroma and time.time() > self._chroma_retry_time:
    self._use_chroma = self._init_chroma()
```

Two threads can concurrently read `self._use_chroma = False`, both enter `_init_chroma()`, and both attempt to create a `PersistentClient` and load `SentenceTransformer`. This doubles initialization work and can cause a race where `self._collection` and `self._embedder` are partially assigned from different invocations.

**Fix:** Add a lock (e.g., `self._chroma_init_lock = threading.Lock()`) around the `_init_chroma` call path in `add()` and `_dedup_exists()`.

### 3. Performance Problems

---

**PERF-01 — `UsageTracker._persist()` writes full JSON synchronously on every `add()`**
Severity: Major | Priority: Medium

Every call to `ask_stream` ends with `_track_usage` → `usage.add(...)` → `_persist()` which does a synchronous `Path.write_text()` of the entire usage JSON. Under high message throughput (autonomy loop running many steps), this means sequential full-file writes after each step. On spinning disk or a slow NFS mount this causes measurable latency spikes.

**Fix:** Debounce the write with a dirty flag and a background thread, or batch writes using `threading.Timer` to flush after a quiet period (e.g., 2 seconds of no `add()` calls).

---

**PERF-02 — `_persist_goals()` called on every step completion with no batching**
Severity: Minor | Priority: Medium

`_on_goal_step_completed()` calls `_persist_goals()` which writes the full `_goals` list to JSON on every step. A 20-step goal executing rapidly triggers 20 sequential file writes. Unlike `_persist_session()`, this does not use a temp-file-then-rename pattern, meaning a crash mid-write can corrupt the goals file.

**Fix:** Use the same atomic write pattern as `_persist_session` (temp file → rename). Consider debouncing to batch writes within a 500ms window.

---

**PERF-03 — Large document ingestion has no chunked embedding batching**
Severity: Minor | Priority: Low

In `rag/doc_store.py`, `ingest()` embeds all chunks in one call:
```python
embeddings = self._embedder.encode([c.text for c in self._docs[filename]])
```

A 300-page PDF produces ~600 chunks. Passing all 600 to `SentenceTransformer.encode()` at once loads the full batch into memory and passes it to the model in one forward pass, which can exhaust RAM on devices with limited VRAM/CPU memory.

**Fix:** Batch the embedding in chunks of, say, 32 or 64 at a time using a simple `for i in range(0, len(chunks), batch_size)` loop.

### 4. Security & Vulnerabilities

---

**SEC-01 — Input length not validated in Telegram or GUI (only CLI has the guard)**
Severity: Critical | Priority: High

`interfaces/cli.py` guards against excessively long input:
```python
if len(user_text) > 50_000:
    ...
    continue
```

But `interfaces/telegram_bot.py` and `interfaces/gui/app.py` have no equivalent guard. A user (or attacker with Telegram access) can send a message of arbitrary length, which flows directly into `ask_stream` → `_context_messages` → `build_system_prompt`, potentially consuming enormous token budgets or causing OOM in the embedding stage.

**Fix:** Apply the same 50,000-character guard (or a tighter limit) in `on_message` in the Telegram bot and in `send_message` in the GUI before calling `agent.ask_stream`.

---

**SEC-02 — PIN lockout file path is current-working-directory-relative**
Severity: Major | Priority: High

```python
# interfaces/cli.py
lock_file = Path(CLI_PIN_LOCK_FILE)  # = ".jarvis/cli_pin.lock"
```

`CLI_PIN_LOCK_FILE = ".jarvis/cli_pin.lock"` is a relative path. If NOVA is started from a different working directory (e.g., `python /opt/nova/main.py` from `/home/user`), the lock file is written to `/home/user/.jarvis/cli_pin.lock`. An attacker can bypass the lockout by simply launching the process from a fresh temp directory. The actual PIN hash file at a fixed user-home path is not bypassed, but the lockout timer is completely circumvented.

**Fix:** Resolve the lockout path against an absolute base — either `Path.home() / ".jarvis/cli_pin.lock"` or `Path(__file__).resolve().parent / ".jarvis/cli_pin.lock"`.

---

**SEC-03 — Rate-limited tool calls are never written to the guardrails audit log**
Severity: Major | Priority: Medium

In `dispatcher.py`:
```python
try:
    self._consume_token()
except RateLimitedError as exc:
    return {"status": "rate_limited", "reason": str(exc)}
```

The rate-limited return path bypasses `guardrails.log(...)`. Repeated high-frequency tool calls (e.g., an autonomy loop hammering `web.search`) that hit the rate limit leave no trace in `logs/guardrails_actions.jsonl`. The audit trail is incomplete, which matters for security review and anomaly detection.

**Fix:** Call `guardrails.log(tool_call, risk, result, status="rate_limited", confirmed_by="system")` before returning from the rate-limited path.

---

**SEC-04 — `_persist_goals()` uses non-atomic write (no temp-file rename)**
Severity: Major | Priority: Medium

```python
def _persist_goals(self) -> None:
    self._goals_file.write_text(json.dumps(...), encoding="utf-8")
```

If the process crashes or is killed mid-write, the goals JSON file is left partially written and becomes invalid JSON. On next startup, `json.loads()` raises `JSONDecodeError` which is caught and logged, but **the entire goal queue is silently lost**. This is a data-integrity risk for long-running autonomy workflows.

**Fix:** Use the same atomic write pattern as `_persist_session`: write to a `.tmp` file, then `Path.replace()`.

---

**SEC-05 — `_PRIVATE_NETWORKS` in `web/scraper.py` is missing the `0.0.0.0/8` range**
Severity: Minor | Priority: Low

The SSRF blocklist covers RFC1918, loopback, link-local, and Tailscale ranges, but omits `0.0.0.0/8` (current network addresses). On some Unix systems, `http://0.0.0.0/` resolves to localhost, which would bypass the SSRF guard. It also omits `240.0.0.0/4` (reserved/broadcast ranges).

**Fix:** Add `ipaddress.ip_network("0.0.0.0/8")` and `ipaddress.ip_network("240.0.0.0/4")` to `_PRIVATE_NETWORKS`.

### 5. Critical System Risks

---

**RISK-01 — `_persist_session()` silently swallows all errors including disk-full**
Severity: Major | Priority: High

```python
def _persist_session(self, session: SessionState) -> None:
    try:
        ...  # write to disk
    except Exception:
        pass  # ← completely silent
```

If the disk is full, a permissions error occurs, or the session directory is deleted, `_persist_session` silently discards all session history from that point forward. The user has no indication their conversation is not being saved. Session recovery on restart will find no file and start fresh.

**Fix:** Log at `WARNING` level at minimum: `logging.getLogger(__name__).warning("Session persist failed for %s: %s", session.name, exc)`.

---

**RISK-02 — `NOVAApp.__init__` shuts down and recreates executors it just created**
Severity: Minor | Priority: Medium

```python
# main.py
self._summarize_executor = ThreadPoolExecutor(max_workers=1)   # created
self._memory_executor    = ThreadPoolExecutor(max_workers=1)
self._goal_plan_executor = ThreadPoolExecutor(max_workers=2)
...
self._summarize_executor.shutdown(wait=False)  # immediately destroyed
self._memory_executor.shutdown(wait=False)
self._goal_plan_executor.shutdown(wait=False)
self._summarize_executor = ThreadPoolExecutor(max_workers=1)   # recreated
self._memory_executor    = ThreadPoolExecutor(max_workers=1)
self._goal_plan_executor = ThreadPoolExecutor(max_workers=2)
```

This pattern creates three thread pools, immediately shuts them down, and recreates identical ones. The first set is dead code. While harmless at runtime, it adds confusion, wastes OS thread creation overhead, and leaves a `shutdown(wait=False)` call that could theoretically race with any stray reference to the first pool.

**Fix:** Remove the first creation block and the `shutdown` calls; keep only the final assignments.

---

**RISK-03 — `_summarize_history_background` exceptions are silently swallowed on `engine.ask()` failure**
Severity: Minor | Priority: Low

```python
def _summarize_history_background(self, text: str, session_id: str) -> None:
    try:
        summary = self.engine.ask(...)
        ...
    except Exception as e:
        logging.getLogger(__name__).warning("Summarizer thread failed unconditionally: %s", e)
```

If `engine.ask` fails (Ollama down, all cloud keys rate-limited), the background summarizer logs a warning but does not mark the session as "needs retry." On subsequent turns, `_summarize_history()` returns `""` from cache and the trimmer degrades to raw truncation indefinitely. There is no backoff or retry signal — the session permanently loses its summary until a fresh restart.

**Fix:** Set a per-session retry timestamp in `_last_snippet_hashes` on failure so the background job is re-enqueued after a delay (e.g., 60 seconds).

---

**RISK-04 — Docker `HEALTHCHECK` uses `ps aux` instead of the health endpoint**
Severity: Minor | Priority: Medium

```dockerfile
HEALTHCHECK --interval=30s --timeout=10s --start-period=10s --retries=3 \
    CMD ps aux | grep 'python3 main.py' | grep -v grep || exit 1
```

This only verifies the process exists, not that it's healthy and responding. NOVA might be stuck in an infinite loop, blocked on DB init, or have crashed its health probe thread — and Docker would still report it as `healthy`. The `_start_probe_server()` method exposes `/health` on `NOVA_HEALTH_PORT` (default 8765) precisely for this purpose.

**Fix:** Replace with `CMD curl -fsS http://localhost:8765/health || exit 1` (curl is already installed in the Dockerfile).

### 6. Minor Issues & Improvements

---

**MINOR-01 — `Mem0Client._call_with_variants` swallows non-`TypeError` exceptions from early variants**
Severity: Minor | Priority: Low

```python
for payload in variants:
    try:
        return fn(**payload)
    except TypeError as exc:
        last_type_error = exc
        continue
    # Any other exception (NetworkError, AttributeError) propagates immediately
```

If variant 1 raises `TypeError` and variant 2 raises `requests.ConnectionError`, the connection error propagates and variants 3 and 4 are never tried. This means a transient network error in an intermediate variant skips potentially-correct variants.

**Fix:** Catch `(TypeError, AttributeError)` (to handle SDK version changes) but still propagate true network errors separately.

---

**MINOR-02 — `XDG_CACHE_HOME` is not passed to the OmniParser subprocess**
Severity: Minor | Priority: Low

`_safe_env()` in `vision/omniparser_server.py` strips all environment variables except a safe subset. It passes `HOME` which allows `~/.cache` to work. However, on systems where `XDG_CACHE_HOME` points to a separate disk/partition for model caches (common in multi-disk setups or Docker with mounted volumes), OmniParser's `transformers` model downloads will silently use `~/.cache` instead, potentially filling the home volume.

**Fix:** Add `"XDG_CACHE_HOME"` to the safe passthrough list in `_safe_env()`.

---

**MINOR-03 — `ask_stream` hard cap and `_track_usage` read `date.today()` independently**
Severity: Minor | Priority: Low

```python
# ask_stream — called at start of request
today = date.today()
with self._usage_lock:
    if self._hard_cap_hit_date != today:
        self._hard_cap_hit = False

# ... LLM call happens (could take 30-90 seconds) ...

# _track_usage — called after LLM responds
# also calls date.today() internally
```

If a request starts just before midnight and finishes just after, `ask_stream`'s `today` is Day N but `_track_usage`'s `date.today()` is Day N+1. The cap check uses Day N's accumulated total, but the usage is recorded against Day N+1. This is an extremely rare edge case but creates a one-message window where the cap check is wrong.

**Fix:** Pass `today` from `ask_stream` into `_track_usage` so both use the same day anchor.

---

**MINOR-04 — `_register_builtin_tools` uses `EmptyArgs` for tools that return data**
Severity: Minor | Priority: Low

Several tools registered with `EmptyArgs` return non-trivial data structures but give the LLM no schema hint:
- `doc.list` → returns `list[dict]`
- `win32_api.list_processes` → returns `list[str]`
- `adb.notifications_dump` → returns a long string
- `adb.sms_dump` → returns a long string

The LLM's tool schema shows `{}` args for these, which is correct. But the return shape is undocumented in the schema prompt. For tools that produce structured output the LLM is expected to parse (like `doc.list`), adding a `description` field to the schema registration would improve LLM reliability.

**Fix:** Consider adding a `docstring` or `description` mechanism to `Dispatcher.register()` and `get_tool_schema_prompt()` so the LLM receives richer hints.

---

**MINOR-05 — `web/scraper.py::_resolve_host` leaks a `ThreadPoolExecutor` thread**
Severity: Minor | Priority: Low

```python
pool = ThreadPoolExecutor(max_workers=1)
fut = pool.submit(_run)
try:
    return fut.result(timeout=timeout_seconds)
except FuturesTimeout as exc:
    fut.cancel()
    raise ValueError(...) from exc
finally:
    try:
        pool.shutdown(wait=False, cancel_futures=True)
    except TypeError:
        pool.shutdown(wait=False)
```

`pool.shutdown(wait=False)` does not kill the running DNS thread — `socket.getaddrinfo` is a blocking C call and ignores Python thread interruption. On DNS timeout, the thread continues running in the background until the OS DNS timeout fires (typically 5-30 seconds). Under heavy scraping workloads this accumulates leaked threads.

**Fix:** Accept this as a platform limitation and document it, or replace with `socket.setdefaulttimeout()` in the thread.

---

**MINOR-06 — `interfaces/cli.py` PIN exponential delay runs before the 5th failure write**
Severity: Minor | Priority: Low

The PIN loop:
```python
while failed < 5:
    entered = getpass.getpass(...)
    if _verify_pin(entered, pin_hash):
        break
    failed += 1
    delay = min(30, 2 ** failed)
    time.sleep(delay)
else:
    lock_file.write_text(str(time.time() + 300), ...)
```

After 5 failures the total wait is 2+4+8+16+30 = 60 seconds before the lockout file is written. If the attacker has a script that kills and restarts the process, they can attempt 5 PINs every 60 seconds without ever triggering the lockout (the lockout file is only written after 5 failed attempts complete, not before). The lockout should be written earlier — ideally after the first failure or using an incremental file.

**Fix:** Write the lockout with an increasing timestamp after each failed attempt, not only after all 5 are exhausted.

---

**MINOR-07 — `_context_messages` submits a background summary job on every turn beyond `max_raw_turns`**
Severity: Minor | Priority: Low

After the conversation exceeds `max_raw_turns` (10), every single call to `_context_messages` creates a new background summarization job (guarded by `_summary_inflight` per session, but not rate-limited beyond that). For sessions with many users (Telegram bot with autonomous autonomy loop), this can queue a large backlog of LLM calls for summarization, adding latency and burning tokens.

**Fix:** Add a minimum re-summary interval (e.g., only re-summarize if more than 3 new turns have been added since the last summarization).

---

**MINOR-08 — `NOVAApp` has no `__del__` or finalizer guard for abandoned instances**
Severity: Minor | Priority: Low

If `NOVAApp.__init__` raises mid-construction, the partially constructed object's threads (TTS worker, any already-started health monitor) are never stopped because `shutdown()` is never called. The `_tts_thread` is a daemon thread so it will be reaped on process exit, but `health.start()` may have already launched a non-daemon-thread-backed monitor.

**Fix:** Add a `try/except` wrapper around the entire init body that calls `self.shutdown()` before re-raising, or make all background threads daemon threads.

---

**MINOR-09 — `session.py::_persist_session` cross-device check silently passes on its own `raise`**
Severity: Minor | Priority: Low

From BUG.TXT RISK-NEW-04, this was listed as a concern. Looking at the current code:
```python
try:
    tmp_dev = tmp_path.stat().st_dev
    dst_dev = sessions_dir.stat().st_dev
except OSError:
    tmp_dev = dst_dev = None
if tmp_dev is not None and dst_dev is not None and tmp_dev != dst_dev:
    raise OSError("temporary file and destination are on different devices...")
```

The `raise OSError(...)` is now outside the `try` block, so it correctly propagates. However, it's then caught by the outer `except Exception: pass` in `_persist_session`. The fix from BUG.TXT was applied but the outer silent swallow remains — this intentional safety raise is silently discarded. On cross-device setups, the non-atomic rename proceeds without any log or user feedback.

**Fix:** Log the cross-device error before it's absorbed by the outer handler.

---

**MINOR-10 — Missing `logs/.gitkeep` and `exports/.gitkeep` for Docker volume mounts**
Severity: Minor | Priority: Low

`docker-compose.yml` mounts `./logs:/app/logs` and `./exports:/app/exports`. On a fresh clone these directories don't exist. Docker creates them as root-owned, causing write-permission errors for NOVA running as a non-root user inside the container. `assets/.gitkeep` exists but the equivalent for `logs/` and `exports/` is absent.

**Fix:** Add `logs/.gitkeep` and `exports/.gitkeep` to the repository and to `.gitignore` exclusions for `*.jsonl` and `*.md` within those directories.

### 7. Missing Features or Components

---

**MISS-01 — No integration tests covering the Telegram bot auth whitelist**
Severity: Major | Priority: Medium

`is_whitelisted()` is unit-tested indirectly via `test_telegram_bot.py`, but no test covers the full handler flow: a non-whitelisted `user_id` reaching `on_message` and being rejected without response. The rejection logging path (fix 1.2 from BUG.TXT) is untested, so a regression in `_authorized()` could silently open the bot to arbitrary users.

**Fix:** Add a test that injects a fake `Update` with a non-whitelisted `user_id` and asserts `_authorized()` returns `False` and logs the rejection.

---

**MISS-02 — No test coverage for `_autonomy_loop` goal state transitions**
Severity: Major | Priority: Medium

The autonomy loop's status transitions (`pending` → `running` → `completed`/`paused`/`failed`/`awaiting_confirmation`) are complex and security-critical (they control when tools execute autonomously). There are zero tests in `tests/` covering `_autonomy_loop` directly, including the `approved_for_step` path identified in BUG-03 above.

**Fix:** Add unit tests using `monkeypatch` to mock `autonomy_runner.run()` return values and assert the goal status transitions.

---

**MISS-03 — No test for `_persist_goals()` atomic-write failure**
Severity: Minor | Priority: Low

Given that `_persist_goals()` uses a non-atomic write (see SEC-04), there is also no test verifying that a corrupt/partial goals file on startup is handled gracefully. The current code catches `JSONDecodeError` and logs a warning, but the test suite doesn't exercise this path.

**Fix:** Add a test that writes invalid JSON to the goals file path and confirms `NOVAApp` starts cleanly with an empty goal list.

### 8. Deployment & Production Readiness

---

**DEPLOY-01 — `requirements.txt` and `requirements.lock` are identical files**
Severity: Minor | Priority: Low

Both files were generated on 2026-03-28 and are byte-for-byte identical. Having two identical files is confusing for contributors who may edit one but not the other. `setup.py` correctly prefers `requirements.lock`, but CI pipelines may target `requirements.txt`.

**Fix:** Delete `requirements.txt` and update any CI scripts or README references to point to `requirements.lock`.

---

**DEPLOY-02 — `DATA_DIR` default is `"~/.jarvis/data"` but `TaskScheduler` uses `Path(__file__).parent.parent` as its data dir**
Severity: Minor | Priority: Medium

In `tasks/scheduler.py`:
```python
_DATA_DIR = Path(os.getenv("DATA_DIR", Path(__file__).resolve().parent.parent)).expanduser().resolve()
```

When `DATA_DIR` is not set in the environment, this resolves to the repository root, not `~/.jarvis/data`. But `config/settings.py` has `DATA_DIR: str = "~/.jarvis/data"`. These two defaults are inconsistent — `TaskScheduler` uses the repo root while `Settings` advertises `~/.jarvis/data`. In Docker, this places `jarvis_jobs.sqlite` in `/app`, which is not a mounted volume and is lost on container restart.

**Fix:** Make `TaskScheduler.__init__` read `settings.DATA_DIR` directly instead of using its own `os.getenv` default.

**DEPLOY-03 — No graceful handling if `NOVA_HEALTH_PORT` (8765) is already in use on startup**
Severity: Minor | Priority: Medium

If port 8765 is taken, `_start_probe_server()` raises `OSError: [Errno 98] Address already in use`. The exception is caught and logged at `ERROR` level, NOVA starts without a health probe, and Docker Compose's `condition: service_healthy` check (which relies on the health endpoint) begins failing immediately. The log message is not visible at startup without checking container logs.

**Fix:** Try an alternate port (e.g., 8766) or expose `NOVA_HEALTH_PORT_FALLBACK` env var; log a prominent startup banner if the health probe couldn't bind.
