Here is the full technical audit of the NOVA project as it stands today, covering only issues found in the current codebase that are not already addressed by BUG.TXT.

## NOVA — Full Technical Audit Report (Current Codebase)

---

### 1. Bugs & Runtime Errors

---

**BUG-NEW-01 — `RoundRobinPool` has no thread-safety for `_keys` and `_index`**
Severity: Major | Priority: High

`get_next()`, `mark_rate_limited()`, `mark_dead()`, and `mark_success()` all mutate `_keys` list entries and `_index` without any lock. When `LLMEngine.ask_stream()` is called concurrently from multiple threads (e.g., autonomy loop and a CLI user simultaneously), `record.failures += 1` is a non-atomic read-modify-write and `self._index = (self._index + 1) % total` is a non-atomic increment. This can corrupt key state and cause pool exhaustion even when live keys remain.

Fix: Add a `threading.RLock` to `RoundRobinPool.__init__` and wrap all public methods that read or write `_keys` or `_index`.

---

**BUG-NEW-02 — `utils/logger.py` has a TOCTOU race in `_ensure_logger_initialized`**
Severity: Major | Priority: High

```python
_logger_initialized = False
def _ensure_logger_initialized():
    global _logger_initialized
    if not _logger_initialized:
        _logger_initialized = True
        setup_logger()
```

Two threads can simultaneously read `_logger_initialized = False`, both enter the block, both call `setup_logger()`, and loguru adds duplicate sinks. Every subsequent log line is written twice to stderr and twice to the rotating file, doubling I/O and causing confusing duplicate output. The fix is a `threading.Lock` around this block.

---

**BUG-NEW-03 — `tray.py::on_health` retries the exact same failing operation**
Severity: Minor | Priority: Low

```python
def on_health(_icon, _item):
    try:
        _notify("NOVA Health", _format_health_summary(agent))
    except Exception:
        try:
            _notify("NOVA Health", _format_health_summary(agent))  # identical call
        except Exception as exc:
            _notify("NOVA Health", f"Health unavailable: {exc}")
```

The inner `try` block is an exact copy of the outer block. If the first call fails, the second call will fail for the same reason. The final `except` block is unreachable because the inner try catches the same exception and calls `_notify` again (which may also fail silently). This is clearly a copy-paste error.

Fix: Remove the inner try block. The final except should call `_notify` directly.

---

**BUG-NEW-04 — `Dispatcher._validate_registration_signature` uses `bind_partial`, which doesn't catch extra schema fields**
Severity: Major | Priority: High

```python
kwargs = {field_name: None for field_name in schema.model_fields.keys()}
signature.bind_partial(**kwargs)
```

`bind_partial` only validates that the provided kwargs are *acceptable*, not that they are *sufficient*. A function `def fn(x: int)` registered with a schema containing fields `{x, y}` will pass this check because `bind_partial(x=None, y=None)` succeeds (Python's `bind_partial` accepts extra kwargs without error for `**kwargs` functions and also doesn't raise for regular kwargs if they partially bind). More critically, a function with `**kwargs` will always pass regardless of schema mismatch.

The real failure is this: if the function does *not* accept `**kwargs`, the `fn(**validated.model_dump())` call in `execute()` will raise `TypeError` at runtime, which is now caught and returned as `"tool_signature_error"`. But the registration-time validation silently passes when it should fail.

Fix: Use `signature.bind(**kwargs)` in `_validate_registration_signature`, which validates all fields are accepted and no unexpected extras are provided.

---

**BUG-NEW-05 — `MemoryRouter.sync_pending` always marks items as synced**
Severity: Major | Priority: High

```python
result = self.mem0.add(item["text"], session_id, item["metadata"])
if result is not None:
    synced.append(item)
else:
    failed.append(item)
```

`Mem0Client.add()` always returns a `dict` — never `None`. When remote is available it returns `{"status": "ok", ...}`, when it falls back to local it returns `{"status": "ok", ...}` or `{"status": "duplicate", ...}`. The `result is not None` check is therefore always `True`, meaning failed items are never tracked in `failed` and are always removed from `_pending_sync` even when the sync silently failed internally. Offline memories that couldn't reach mem0 are dropped silently.

Fix: Check `result.get("status") in {"ok"}` or catch exceptions specifically for the remote path.

---

**BUG-NEW-06 — `GoalRunner.run()` creates a new `ThreadPoolExecutor` for every step**
Severity: Major | Priority: High

```python
pool = ThreadPoolExecutor(max_workers=1)
future = pool.submit(self.dispatcher.execute, call, None, None, dry_run, True)
try:
    result = future.result(timeout=self.step_timeout_seconds)
...
finally:
    pool.shutdown(wait=False)
```

For a 20-step goal, this creates and destroys 20 thread pools. Each `ThreadPoolExecutor` spawns an OS thread that lingers until garbage collection. Under concurrent goal execution (autonomy + manual), this can exhaust thread limits. `pool.shutdown(wait=False)` also doesn't guarantee cleanup, and `cancel_futures=True` is conditionally applied only in Python 3.9+.

Fix: Create one executor per `GoalRunner` instance in `__init__` and reuse it across steps.

---

**BUG-NEW-07 — `QRPairing.local_ip()` leaks a socket on exception**
Severity: Minor | Priority: Low

```python
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
sock.connect(("8.8.8.8", 80))
ip = sock.getsockname()[0]
sock.close()
```

If `sock.connect()` raises an `OSError` (e.g., no network), the socket is never closed. Over multiple failed calls this leaks file descriptors.

Fix: Wrap in a `try/finally` block or use the socket as a context manager.

---

**BUG-NEW-08 — `_autonomy_loop` shallow-copies `_goals` but accesses dict references without locking**
Severity: Major | Priority: Medium

```python
with self._goal_lock:
    goals_snapshot = list(self._goals)

for item in goals_snapshot:
    if item.get("status") in {"pending", ...}:
        candidate_id = item.get("id")
```

`list(self._goals)` creates a shallow copy — `item` is a reference to the same dict object still being mutated by `_on_goal_step_completed` in the background. Reading `item.get("status")` outside the lock is a data race. If another thread writes to that dict concurrently, the read may observe a partial update.

Fix: Use `copy.deepcopy(self._goals)` inside the lock, or only read the `id` and `status` fields atomically inside the lock before releasing it.

---

**BUG-NEW-09 — `_goal_plan_executor.shutdown(wait=True)` in `shutdown()` can hang indefinitely**
Severity: Major | Priority: High

```python
self._goal_plan_executor.shutdown(wait=True, **kwargs)
```

If a background planning call is blocked waiting for an LLM response (network timeout can be 90 seconds per `LLMEngine`), `shutdown(wait=True)` will block the main thread for the full timeout duration. `app.shutdown()` is called on `SIGTERM` and `SIGINT`, so process termination is blocked.

Fix: Use `shutdown(wait=False, cancel_futures=True)` and use `_shutting_down` event to abort in-flight planning calls.

---

**BUG-NEW-10 — Session name collision in `_persist_session`**
Severity: Minor | Priority: Medium

```python
safe_name = "".join(c if c.isalnum() or c in "_-" else "_" for c in session.name)
```

Session names `"a.b"` and `"a_b"` both sanitize to `"a_b"`, causing them to share the same file path. The second session's history would overwrite the first's file silently.

Fix: Use a hash suffix to disambiguate: `safe_name + "_" + hashlib.sha256(session.name.encode()).hexdigest()[:8]`.

### 2. Connectivity & Integration Issues

---

**CONN-NEW-01 — Telegram bot runs synchronous generator in async handler**
Severity: Major | Priority: High

```python
for token in agent.ask_stream(prompt_text):
    buffer += token
    now = time.time()
    if now - last_edit > 1.5:
        await context.bot.edit_message_text(...)
```

`agent.ask_stream()` is a synchronous generator. Calling it inside an `async def` handler with `python-telegram-bot` v20+ blocks the asyncio event loop for the entire duration of the LLM call. No other Telegram updates (commands, messages) can be processed while a response is being generated. In a busy bot, this causes request queuing and timeout errors.

Fix: Run `ask_stream()` in a thread executor: `await asyncio.get_event_loop().run_in_executor(None, ...)` or rewrite `ask_stream` as an `async` generator.

---

**CONN-NEW-02 — `LocalMemoryStore._dedup_exists` floods ChromaDB on startup**
Severity: Minor | Priority: Medium

```python
def _dedup_exists(self, hash_id: str) -> bool:
    import time
    if not self._use_chroma:
        if time.time() > self._chroma_retry_time:
            self._use_chroma = self._init_chroma()
```

`_chroma_retry_time` is initialized to `0.0`. Since `time.time()` is always greater than 0, every `add()` call before ChromaDB is available will attempt `_init_chroma()`. If `_init_chroma()` takes 200ms to fail (connection timeout), and `add()` is called frequently, this generates a continuous stream of connection attempts. The retry time is only set to `now + 60.0` in the `add()` method, not inside `_dedup_exists`.

Fix: Set `self._chroma_retry_time = time.time() + 60.0` inside `_dedup_exists` immediately after `_init_chroma()` fails.

### 3. Performance Problems

---

**PERF-NEW-01 — Web crawler has an unbounded queue**
Severity: Major | Priority: Medium

```python
for link in soup.find_all("a", href=True):
    nxt = urljoin(url, link["href"])
    if urlparse(nxt).netloc == domain and nxt not in seen:
        queue.append((nxt, depth + 1))
```

A single page with 5,000 links (e.g., a Wikipedia article with extensive navigation) adds 5,000 entries to the queue before any of them are visited. `max_pages` limits total pages visited but not queue size. A crawler called with `max_pages=5` on a content-heavy page could queue thousands of URLs consuming significant memory and making the early termination condition unpredictable.

Fix: Cap queue growth: `if len(queue) < max_pages * 10: queue.append(...)`.

---

**PERF-NEW-02 — `ContextTrimmer.trim()` holds the lock while calling `summarizer()`**
Severity: Minor | Priority: Medium

```python
with self._lock:
    ...
    compressed = summarizer(snippet) if summarizer else snippet[:700]
```

The RLock is held for the entire duration of the summarizer call. In production, `_summarize_history()` does a dict lookup (fast), but any future summarizer that makes a blocking call would stall all concurrent `trim()` calls. The summary computation should happen outside the lock, with only the write-back locked.

---

**PERF-NEW-03 — `_summarize_executor` and `_memory_executor` have no maximum queue size**
Severity: Minor | Priority: Low

Both `ThreadPoolExecutor(max_workers=1)` instances have unbounded work queues. Under sustained high message throughput (e.g., autonomy loop running many steps rapidly), `_commit_memory_async` and background summarization tasks can accumulate thousands of queued jobs before they're processed. This consumes memory and delays acknowledgment of memory writes.

Fix: Use a bounded queue via a custom executor or track in-flight job count and skip new submissions if the queue is too deep.

### 4. Security & Vulnerabilities

---

**SEC-NEW-01 — OmniParser auth token exposed in process command line**
Severity: Major | Priority: High

```python
command = [
    sys.executable, "-m", "vision.omniparser_app",
    "--auth-token", self.auth_token,
]
```

The auth token is passed as a command-line argument and is visible to all users on the system via `ps aux`, `/proc/<pid>/cmdline`, and system monitoring tools. On any multi-user system, this fully defeats the authentication mechanism.

Fix: Pass the token via an environment variable set only in `_safe_env()`:
```python
env["OMNIPARSER_AUTH_TOKEN"] = self.auth_token
```
Then read it in `omniparser_app.py` with `os.environ.get("OMNIPARSER_AUTH_TOKEN")`.

---

**SEC-NEW-02 — CLI and GUI PIN has no brute-force protection**
Severity: Major | Priority: High

```python
if pin_hash:
    entered = getpass.getpass("Enter CLI PIN to unlock NOVA: ")
    if not _verify_pin(entered, pin_hash):
        print("Access Denied.")
        return
```

There is no attempt counter, no lockout, no delay after failed attempts. An attacker with local access can try PINs programmatically by restarting the CLI in a loop. A 4-digit PIN has only 10,000 combinations and can be exhausted in seconds.

Fix: Add an exponential delay after each failed attempt (e.g., `time.sleep(2 ** failed_attempts)`) and lock out after 5 consecutive failures by writing a lock file.

---

**SEC-NEW-03 — `approved_for_step` auto-confirms ALL remaining steps in a goal**
Severity: Major | Priority: High

In `_autonomy_loop`:
```python
if approved_for_step:
    result = self.autonomy_runner.run(
        steps, ...
        confirm_callback=lambda _p: True,  # approves everything
    )
```

When the user approves a single paused step with `/approve_goal`, the confirm callback is set to `lambda _p: True` for the entire remaining run. If the goal has 20 steps and step 5 required approval, steps 6–20 are all auto-approved and execute without user confirmation, even if they are high-risk tool calls. A malicious LLM response could embed destructive steps after the approved one.

Fix: The `approved_for_step` flag should only override confirmation for the single next step (`start_index` to `start_index + 1`), then revert to `self._autonomy_confirm_callback` for all subsequent steps.

---

**SEC-NEW-04 — `scrape_text` SSRF protection has no redirect following guard**
Severity: Major | Priority: Medium

`_validate_url()` resolves the initial URL's hostname and blocks private IPs. However, if the server responds with an HTTP 301/302 redirect to `http://192.168.1.1/admin`, the `requests.get()` call will follow the redirect automatically and hit the internal address. The SSRF guard only validates the initial URL, not redirect destinations.

Fix: Pass `allow_redirects=False` and manually validate each redirect destination, or validate that the final response URL passes `_validate_url()`.

---

**SEC-NEW-05 — Plugin sandbox `exec` uses shared `restricted_globals` between AST check and execution**
Severity: Minor | Priority: Medium

```python
_check_ast(source)
code = compile(source, str(path), "exec")
exec(code, restricted_globals)
```

`_check_ast` only inspects AST nodes statically. A plugin can pass AST inspection but use runtime techniques like `type.__subclasses__()`, accessing `__class__.__mro__` chains, or constructing strings and passing them to `eval` via overridden `__str__` methods. The sandbox provides a meaningful but not complete security boundary. Plugins should be explicitly documented as "trusted code only."

### 5. Critical System Risks

---

**RISK-NEW-01 — `NOVAApp.__init__` has no partial-initialization guard in `shutdown()`**
Severity: Major | Priority: High

If any component in the `NOVAApp.__init__` chain raises before all attributes are set (e.g., `TaskScheduler()` fails on a locked SQLite DB, or `MemoryRouter()` raises), the partially constructed object may still have `shutdown()` called on it (e.g., by the signal handler). Accessing `self.scheduler.stop()` when `self.scheduler` was never assigned raises `AttributeError` in the shutdown path, hiding the original error.

Fix: Initialize all attributes to `None` at the start of `__init__`, and add `if self.scheduler is not None:` guards in `shutdown()`.

---

**RISK-NEW-02 — `_emergency_stop_paths()` called at module import time before settings are loaded**
Severity: Major | Priority: High

```python
# Module-level, executed at import
_EMERGENCY_STOP_FILE, _EMERGENCY_STOP_FILE_FALLBACK = _emergency_stop_paths()
```

`_emergency_stop_paths()` reads `settings.EMERGENCY_STOP_FILE`. The `guardrails.py` module is imported by `dispatcher.py`, which is imported by `main.py` before `settings` is fully validated. If `settings.py` fails to load `.env` (e.g., missing file), the emergency stop path uses defaults, but the `_EMERGENCY_STOP_FILE` module-level variable is frozen at that default and never updated if settings change. In tests, this means the emergency stop file path is computed before `monkeypatch` can override settings.

Fix: Compute the paths lazily in `Guardrails.__init__` or via a property, not at module level.

---

**RISK-NEW-03 — Memory loss if `_summarize_executor` has a queued summary job when `shutdown()` is called**
Severity: Minor | Priority: Medium

```python
self._summarize_executor.shutdown(wait=False, **kwargs)
```

Background summarization jobs that are queued but not yet started are discarded. The trimmer summary for the current session is then lost. On next startup, the context trimmer starts fresh with an empty summary, losing the compressed history of the conversation. The `wait=False` is intentional (to avoid blocking on shutdown), but there's no mechanism to flush or persist the pending summary before abandoning the executor.

Fix: Before calling `shutdown()`, attempt a short `wait=True` with a timeout, or persist the current `trimmer.summaries` dict to disk as part of session persistence.

---

**RISK-NEW-04 — `core/session.py` cross-device rename check can silently fail**
Severity: Minor | Priority: Low

```python
try:
    if tmp_path.stat().st_dev != sessions_dir.stat().st_dev:
        raise OSError("temporary file and destination are on different devices...")
except Exception:
    pass
```

The cross-device check is wrapped in a bare `except Exception: pass`. If the stat fails for any reason (e.g., the temp file was already cleaned up, or an access error), the exception is silently discarded and `tmp_path.replace(path)` proceeds with potentially non-atomic behavior. More importantly, the `raise OSError` inside the try is also caught by the `except Exception: pass`, meaning the check never actually prevents the non-atomic rename.

Fix: Separate the device check into its own try/except that only ignores `OSError` from `stat()`, not the intentional raise.

### 6. Minor Issues & Improvements

---

**MINOR-NEW-01 — `LLMEngine.ask_stream` has fragile generator abandonment detection**
Severity: Minor | Priority: Low

The `finally` block in `ask_stream` persists partial output when the generator is abandoned mid-stream. However, `committed = False` is checked in the finally, but `committed` is only set to `True` after successful `_commit_memory_async()`. If the caller fully consumes all tokens but abandons before the `tool_call` execution block, `committed` stays `False` and the finally block double-calls `add_turn("assistant", ...)` — once in the try block and once in the finally.

Fix: Set `committed = True` immediately after `add_turn("assistant", ...)` in the main try path, not after `_commit_memory_async()`.

---

**MINOR-NEW-02 — `interfaces/cli.py` and `interfaces/gui/app.py` use slightly different PIN file paths**
Severity: Minor | Priority: Low

CLI reads from `.jarvis/cli_pin_hash` then `.jarvis/cli_pin`. GUI reads the same paths. But the file paths are hardcoded twice in two different modules. If the path changes in one module, the other silently diverges, creating a situation where CLI authentication works but GUI doesn't (or vice versa).

Fix: Move the PIN file paths to `config/constants.py` as `CLI_PIN_HASH_FILE = Path(".jarvis/cli_pin_hash")`.

---

**MINOR-NEW-03 — `core/plugin_loader.py` allows plugins to shadow tools registered before them**
Severity: Minor | Priority: Medium

```python
if name in dispatcher.registry:
    logging.getLogger(__name__).warning(
        "Plugin attempted to shadow builtin tool '%s'. Skipping.", name
    )
    continue
```

This check only prevents shadowing tools registered before `load_plugins()` is called. If two plugins both define the same tool name, the first plugin's tool is registered, and the second plugin's tool is silently skipped (the check passes for the first plugin but catches the second). There is no warning that the second plugin partially loaded.

---

**MINOR-NEW-04 — `web/crawler.py` depth tracking does not limit link discovery**
Severity: Minor | Priority: Low

`max_depth` correctly prevents visiting pages beyond the depth limit, but pages at `depth = max_depth` still have all their links added to the queue (they just aren't visited because `if depth >= max_depth: continue`). The queue is populated but then each enqueued link is immediately skipped. This wastes memory and iteration time.

Fix: Only discover links when `depth < max_depth`:
```python
if depth < max_depth:
    for link in soup.find_all("a", href=True):
        ...
```

---

**MINOR-NEW-05 — `config/settings.py` `_is_placeholder_key` entropy check is weak**
Severity: Minor | Priority: Low

```python
unique_chars = len(set(k))
if unique_chars < 6:
    return True
```

A key of `"aaaaaabcde"` (5 unique chars) is correctly flagged, but `"aaaaaa1234567890123456"` (10 unique chars, 22 chars long) passes all checks despite being clearly a test value with low entropy. The entropy check should use Shannon entropy rather than a simple unique-character count.

---

**MINOR-NEW-06 — `vision/omniparser_server.py` blocks the `ensure_running()` deadline with exponential backoff**
Severity: Minor | Priority: Low

```python
delay = 1.0
while time.monotonic() < deadline:
    if self.is_running():
        return
    attempt += 1
    wait = min(delay * (2 ** (attempt - 1)), 16.0)
    time.sleep(wait)
```

After 5 attempts, `wait = 16.0s`. If the deadline is 120s, the loop only has time for about 7 attempts (1 + 2 + 4 + 8 + 16 + 16 + 16 = 63s, then one more check). The process startup could succeed between two checks but the long sleep delays detection. Use a shorter max backoff (e.g., 4s) for server health checks.

### 7. Missing Features or Components

---

**MISS-NEW-01 — No test coverage for `control/adb/` modules**
Severity: Major | Priority: Medium

`control/adb/adb_client.py`, `control/adb/watcher.py`, and `control/adb/tailscale.py` have partial coverage in `tests/test_adb_tools.py` (mostly QR and tailscale), but `ADBClient.send_sms`, `ADBClient.notifications_dump`, `PhoneWatcher._poll_sms`, and `PhoneWatcher._tick` are untested. These are the most security-sensitive ADB operations.

---

**MISS-NEW-02 — No test coverage for `core/context/environment.py` stale-cache path**
Severity: Minor | Priority: Low

The stale-cache return-and-background-refresh path in `snapshot_environment()` has no tests. A regression here would silently cause the world state in every LLM prompt to be stale, degrading response quality without any error signal.

---

**MISS-NEW-03 — `NOVAApp` has no health check for the probe server itself**
Severity: Minor | Priority: Low

`_start_probe_server()` launches a `ThreadingHTTPServer` in a daemon thread. If the thread crashes (e.g., port already in use, OS error), the health monitor doesn't know — `NOVA_HEALTH_PORT` returns nothing, and Docker/k8s health checks start failing. The `health` subsystem should register a check: `self.health.register_subsystem("probe_server", check_fn=lambda: self._health_http_server is not None)`.

---

**MISS-NEW-04 — No persistence mechanism for `UsageTracker` across restarts**
Severity: Minor | Priority: Medium

`UsageTracker` stores all data in an in-memory dict. On process restart, all token usage history is lost. The `DAILY_TOKEN_HARD_CAP` check resets to zero on restart, meaning the hard cap can be bypassed by restarting the agent. In production, this is a billing risk.

Fix: Persist the daily usage dict to a SQLite file or JSON file, flushed after each `add()`.

---

**MISS-NEW-05 — No rate limiting on `goal.add` tool calls from the LLM**
Severity: Major | Priority: Medium

The LLM can call `goal.add` as a tool. Each call spawns a background `_goal_plan_executor` future that makes one or more LLM requests. A misconfigured prompt or an adversarial input could cause the agent to call `goal.add` in a loop, spawning hundreds of planning futures and exhausting both thread and token budgets.

Fix: Cap the number of pending goals: if `len([g for g in self._goals if g["status"] in {"planning", "pending"}]) >= MAX_PENDING_GOALS`, reject new `goal.add` calls with a structured error.

---

### 8. Deployment & Production Readiness

---

**DEPLOY-NEW-01 — `docker-compose.yml` NOVA service has no restart delay after dependencies**
Severity: Minor | Priority: Medium

The NOVA service `depends_on` all three other services with `condition: service_healthy`. However, ChromaDB and Ollama may be technically healthy (responding to health endpoints) before they have fully initialized their storage. NOVA startup proceeds immediately and ChromaDB vector operations may fail during the first few seconds with `Collection not found` or similar errors.

Fix: Add a `NOVA_STARTUP_DELAY_SECONDS` env var and sleep that many seconds at the start of `main()` in Docker-only mode.

---

**DEPLOY-NEW-02 — `requirements.txt` and `requirements.lock` are identical but `Dockerfile` installs from `requirements.lock` while `setup.py` installs from `requirements.txt`**
Severity: Minor | Priority: Low

This was noted in BUG.TXT as DEPLOY-02, but the current `setup.py` shows:
```python
req_file = "requirements.lock" if (REPO_ROOT / "requirements.lock").exists() else "requirements.txt"
```
This is now correctly resolved — `setup.py` prefers `requirements.lock`. However, the two files are still identical and should be consolidated. Having two files with identical content is confusing for contributors.

---

**DEPLOY-NEW-03 — `DATA_DIR` default is `"."` which resolves to the working directory**
Severity: Minor | Priority: Medium

`settings.DATA_DIR = "."` means `_DEFAULT_DB` in `tasks/scheduler.py` places `jarvis_jobs.sqlite` in whatever directory the process was started from. In Docker, if the working directory changes (e.g., a future Dockerfile restructure changes `WORKDIR`), the scheduler database silently moves. The `DATA_DIR` should default to a fixed path like `/app/data` in Docker and `~/.jarvis/data` natively.

---

**DEPLOY-NEW-04 — No `logs/.gitkeep` or `exports/.gitkeep` for Docker volume mount directories**
Severity: Minor | Priority: Low

`docker-compose.yml` mounts `./logs:/app/logs` and `./exports:/app/exports`. On a fresh clone, these directories don't exist. Docker will create them as root-owned directories, causing permission errors when NOVA (running as a non-root user) tries to write logs. `assets/.gitkeep` exists but the equivalent for `logs/` and `exports/` is missing.

Fix: Add `logs/.gitkeep` and `exports/.gitkeep` to the repository.

---

**DEPLOY-NEW-05 — No graceful handling when `NOVA_HEALTH_PORT` is already in use**
Severity: Minor | Priority: Medium

```python
server = ThreadingHTTPServer(("0.0.0.0", int(settings.NOVA_HEALTH_PORT)), _ProbeHandler)
```

If port 8765 is already in use, `ThreadingHTTPServer` raises `OSError: [Errno 98] Address already in use`. This exception is caught by:
```python
try:
    self._start_probe_server()
except Exception as exc:
    logging.getLogger(__name__).warning("Health probe startup failed: %s", exc)
```

So NOVA starts without a health probe, but Docker health checks (`condition: service_healthy` in compose) will then fail, causing `nova` to be considered unhealthy and potentially restarted in a loop. The error message in logs is not surfaced prominently.

Fix: Log the error at `ERROR` level and expose a `NOVA_HEALTH_PORT` env fallback that tries the next available port.
