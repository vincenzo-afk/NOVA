## PROACTIVE INTELLIGENCE TIER 1 — Perception Layer

### Continuous Semantic Work Context Graph

- **Trigger**: Every `ScreenWatcher._tick()` cycle (currently every 30s per `settings.PROACTIVE_WATCHER_INTERVAL`)
- **Mechanism**: `ScreenWatcher._tick()` calls `analyze_image()` and `self.omniparser.ocr_text()` but throws away the structured result after checking `_detect_issue()`. A new `WorkContextTracker` class should intercept the full `analysis: dict` from `analyze_image()` and the `ui_elements` list from `OmniParserClient.ui_elements()` *before* `_detect_issue()` discards them. Maintain a rolling `deque[WorkContextFrame]` (last 20 frames) with fields: `active_app`, `scene_type`, `visible_text_hash`, `ui_element_fingerprint`, `timestamp`. On each tick, compute a *context drift score* by comparing the current frame against the last 5. If drift score exceeds threshold AND no alert fired, call a new `_infer_work_context_change()` hook in `NOVAApp._handle_proactive_alert`.
- **Action**: NOVA silently pre-loads relevant `DocumentStore` chunks and `MemoryRouter` memories for the detected context. If user switches from a browser to a terminal, NOVA pre-fetches recent git log, last error from logs, and relevant code memories — all without any output.
- **Output**: Silent pre-load only. No user notification unless the drift triggers an active transition (e.g., switching from writing to debugging).
- **Safeguard**: The existing `cooldown_seconds` in `ScreenWatcher.__init__` applies. Pre-load is capped at 3 `DocumentStore.query()` calls per context switch and runs on `NOVAApp._memory_executor` (already exists) so it cannot block the main loop.
- **Competitive Edge**: AutoGen and CrewAI have no screen awareness whatsoever. Open Interpreter can see the screen on demand but builds no temporal context graph. This is NOVA maintaining a *rolling understanding* of what the developer is doing — not a snapshot.

### Clipboard Content Intelligence Pipeline

- **Trigger**: `snapshot_environment()` in `core/context/environment.py` already calls `_get_clipboard()` but `settings.INCLUDE_CLIPBOARD_IN_CONTEXT` defaults `False` and the clipboard content is only injected as a passive string. The trigger here is a *content-type change* in clipboard — not just "did the clipboard change" but "what category of thing was just copied."
- **Mechanism**: In `_refresh_background()` inside `environment.py`, after `_get_clipboard()`, run a 3-way classifier (regex-based, zero LLM cost): `CODE_BLOCK` (contains `def `, `class `, `import `, `{`, `;`), `ERROR_TRACE` (contains `Traceback`, `Error:`, `Exception`), `URL` (`http://` or `https://`). Store the classified result in `_ENVIRONMENT_CACHE` under a new `clipboard_type` key. In `NOVAApp._context_messages()`, inspect `world_state["clipboard_type"]` — if `ERROR_TRACE`, call a new `_prefetch_error_context(clipboard_text)` that runs `MemoryRouter.search(clipboard_text, session_id, top_k=5)` and stores the result in `NOVAApp._prefetch_cache` (a simple `dict` with TTL).
- **Action**: When the user's next message arrives and `_prefetch_cache` is populated for the current session, those memories are injected into `_context_messages()` *ahead of* the standard memory search, effectively giving NOVA a head start on the answer.
- **Output**: Invisible to the user — the answer simply arrives faster and more accurately.
- **Safeguard**: `_prefetch_cache` TTL is 90 seconds. Clipboard content longer than 4000 chars is truncated before classification. The existing `_scrub_args` pattern in `safety/guardrails.py` is extended to strip clipboard content from any logs.
- **Competitive Edge**: No open-source assistant prefetches context based on clipboard semantic type. This specifically addresses the "I copied an error, now I'm about to ask about it" pattern — one of the highest-frequency developer interactions.

### File System Event Watcher

- **Trigger**: File saves in directories that `DocumentStore` has previously ingested (tracked via `DocumentStore._doc_meta` which already stores `filepath`).
- **Mechanism**: On `NOVAApp.__init__`, after `DocumentStore` is initialized, iterate `self.docs._doc_meta` to collect all watched directories. Use `watchdog` (add to `requirements.txt`) to create a `FileSystemEventHandler` subclass `NOVADocRefreshHandler`. On `on_modified` events matching ingested filenames, call `self.docs.update(filepath)` — which already exists in `rag/doc_store.py` as `DocumentStore.update()`. Register this watcher on `NOVAApp._memory_executor` so file I/O doesn't block the main thread. Additionally, watch `.git/COMMIT_EDITMSG` in the current working directory — on change, extract the commit message and call `MemoryRouter.add(f"Git commit: {msg}", session_id, {"source": "git"})`.
- **Action**: RAG store stays fresh without any user command. Git commit history becomes searchable memory automatically.
- **Output**: None unless the file update triggers a downstream goal (e.g., a scheduled job that depends on the file). NOVA can mention "I noticed you updated `config.py` — I've refreshed my understanding of it" the next time the file is referenced in conversation.
- **Safeguard**: `DocumentStore.update()` calls `delete()` then `ingest()`. Rate-limit to one re-ingest per file per 30 seconds. Maximum 50 watched paths total (prevent inotify descriptor exhaustion). Respect `MAX_DOC_SIZE_BYTES = 50MB` already defined in `rag/doc_loader.py`.
- **Competitive Edge**: Every RAG-based assistant requires manual re-ingestion when files change. NOVA's store self-heals in real time.

### Process Lifecycle Delta Monitor

- **Trigger**: `win32_api.list_processes()` exists but is never called proactively. Add a 60-second poll via `TaskScheduler.add_interval()` during `NOVAApp._start_health_monitoring()`.
- **Mechanism**: Maintain `_last_process_set: set[str]` on `NOVAApp`. On each poll, call `win32_api.list_processes()`, compute `appeared = current - last` and `disappeared = last - current`. For appeared processes, look up a static `PROCESS_CONTEXT_MAP` dict (e.g., `{"zoom": "meeting", "pycharm": "python_dev", "docker": "containerized_workload", "obs": "recording"}`). If a known process appears, fire `NOVAApp._handle_proactive_alert()` with a structured event carrying the context label. This feeds `EmotionEngine.update_from_signal()` — "meeting detected" → `cautious` state; "obs detected" → `focused` state.
- **Action**: NOVA silently switches `EmotionEngine` state, pre-mutes TTS if `zoom` or `teams` is detected, and queues a session switch check (work vs personal based on process signature).
- **Output**: If TTS was active and a meeting app appeared, NOVA sends one Telegram message: "I've paused voice output — looks like you're in a call." Otherwise silent.
- **Safeguard**: Process list is never sent to LLM. The `PROCESS_CONTEXT_MAP` lookup is purely local dictionary matching. Auto-mute only applies if `settings.VOICE_BARGEIN_ENABLED` is True.
- **Competitive Edge**: No existing open-source assistant detects meeting software and self-silences. This eliminates the embarrassing "NOVA is talking loudly while you're on a client call" failure mode.

## PROACTIVE INTELLIGENCE TIER 2 — Inference Layer

### Behavioral Rhythm Modeler

- **Trigger**: Every `NOVAApp._track_usage()` call (currently fired after every `ask_stream()` completion) and every `ScreenWatcher._tick()`.
- **Mechanism**: Create `utils/behavior_model.py` with class `BehaviorModel`. It maintains a persistent `dict` (serialized to `.jarvis/behavior_model.json`) with structure: `{weekday: {hour: {app: count, topic_cluster: count, avg_session_length: float}}}`. In `NOVAApp._track_usage()`, after the existing token tracking, call `behavior_model.record_activity(provider, hour=datetime.now().hour, weekday=datetime.now().weekday(), session_id=session_id)`. In `ScreenWatcher._tick()`, after `analyze_image()`, call `behavior_model.record_screen_state(active_app, scene_type, hour)`. The `BehaviorModel` exposes `predict_next_activity(current_hour, weekday) -> list[str]` using simple frequency-weighted ranking over the last 30 days of observations.
- **Action**: Feeds into `Tier 3` anticipation — NOVA uses predicted next activity to pre-warm relevant tool registrations and memory searches.
- **Output**: Exposed as a new `behavior.profile` tool registered in `NOVAApp._register_builtin_tools()` so the user can query it: "What do I usually do at this time on Tuesdays?"
- **Safeguard**: All data stored locally in `.jarvis/`. Added to `.gitignore` (already has `.jarvis/` entry). No behavioral data ever sent to mem0 or external services. `BehaviorModel` has a `privacy_mode: bool` flag that disables all recording when set.
- **Competitive Edge**: CrewAI and AutoGen operate on task-level instructions with no awareness of the human's temporal work rhythm. This creates genuine personalization that deepens over weeks.

### Intent Graph Builder

- **Trigger**: Every `_commit_memory_async()` call in `NOVAApp` — currently fires `MemoryRouter.add()` with flat text. Add a secondary async step on `NOVAApp._memory_executor`.
- **Mechanism**: Create `core/memory/intent_graph.py` with class `IntentGraph`. It wraps a ChromaDB collection named `"nova_intent_graph"` (separate from `"jarvis_memory"`). After `MemoryRouter.add()` succeeds, extract a lightweight intent tuple from the conversation turn using a fast local LLM call via `LLMEngine.ask()` with a compact system prompt: `"Extract: (verb, object, context) from this exchange. Return JSON only."` Store the tuple as a node. On the second occurrence of the same `(verb, object)` pair, create an edge with weight. Expose `IntentGraph.most_common_intents(session_id, top_k=5) -> list[tuple]` and `IntentGraph.predict_next_intent(current_verb, current_object) -> list[tuple]`.
- **Action**: `IntentGraph.predict_next_intent()` is called at the start of every `ask_stream()` invocation, before the LLM call. The top predicted intent is injected as a silent hint into the system prompt: `"Based on prior patterns, the user may next want to: [predicted_intent]. Pre-consider this."`.
- **Output**: Invisible to the user. The LLM's responses become subtly more anticipatory.
- **Safeguard**: Intent extraction LLM call is made only every 5th conversation turn (tracked by a counter on `SessionState`) to avoid token cost spiral. Intent nodes are capped at 10,000 total across all sessions — oldest are pruned when exceeded.
- **Competitive Edge**: AutoGen's memory systems store facts, not *intent transition probabilities*. This is a Markov-style intent model that makes NOVA's responses statistically aligned with how the user thinks, not just what they said.

### Emotional Trajectory Predictor

- **Trigger**: Currently `EmotionEngine.update_from_signal()` only reacts to the current input. New trigger: a background thread that samples `BehaviorModel` + `ScreenWatcher._last_seen_summary` + current time every 10 minutes.
- **Mechanism**: Add `EmotionEngine.predict_from_context(hour: int, weekday: int, recent_errors: int, session_length_minutes: float) -> str` to `core/emotion/engine.py`. Implement a simple decision tree: if `hour >= 22 and session_length_minutes > 180` → `"empathetic"`; if `recent_errors >= 3` → `"urgent"`; if `weekday in {0,1}` and `hour in range(9, 11)` → `"focused"`. The `recent_errors` count comes from a new counter `NOVAApp._error_detections_this_hour` incremented in `_handle_proactive_alert()` when `"error"` is in the alert message. In `NOVAApp._start_health_monitoring()`, add a 10-minute `TaskScheduler` interval job that calls this predictor and calls `self.emotion.update_from_signal(predicted_state)` only if the current state is `"neutral"` (don't override an already-active state).
- **Action**: NOVA's tone shifts proactively before the user even types. At 11pm after a long debugging session, NOVA switches to empathetic mode — shorter responses, gentler phrasing, occasional "you've been at this for 3 hours, want to call it?" check-in.
- **Output**: The TTS prosody (via `voice/tts.py`'s `_emotion_hint()`) and `build_system_prompt()` emotion parameter shift automatically.
- **Safeguard**: Predicted emotion only takes effect if current `EmotionEngine.state == "neutral"`. User can always say "focus mode" to override.
- **Competitive Edge**: No open-source assistant models emotional trajectory. They react to tone in text; NOVA predicts *need states* from behavioral signals before text is even typed.

### Cross-Session Insight Extractor

- **Trigger**: `ContextTrimmer.trim()` in `core/memory/context_trimmer.py` runs `_summarize_history_background()` for a single session. Add a new weekly cross-session analysis job.
- **Mechanism**: Add `utils/insight_extractor.py` with `InsightExtractor.extract_weekly_themes(session_ids: list[str]) -> list[str]`. On every Sunday at 2:30am (registered via `schedule_daily_backup` pattern in `main.py`), call `MemoryRouter.get_all(session_id)` for all known sessions, concatenate the last 200 memory texts, call `LLMEngine.ask()` with prompt: `"Identify 5 recurring themes, unresolved problems, or emerging patterns across these work sessions. - **Output**: One Telegram message on first Monday activity. Also stored as a memory so it persists and can be queried.

## PROACTIVE INTELLIGENCE TIER 3 — Anticipation Engine

### Predictive Goal Synthesizer

- **Trigger**: `BehaviorModel.predict_next_activity()` returns a prediction with confidence >= 0.7 AND the predicted activity has a corresponding entry in a new `GoalTemplateLibrary` (see Tier 5). Also triggered when `IntentGraph.predict_next_intent()` returns a multi-step sequence that maps to a known template.
- **Mechanism**: Add `core/goals/proactive_goal_engine.py` with class `ProactiveGoalEngine`. It holds a `GoalTemplateLibrary` (simple JSON file at `.jarvis/goal_templates.json`) mapping activity patterns to pre-validated step sequences. On trigger, `ProactiveGoalEngine.propose_goal(context: dict) -> dict | None` generates a candidate goal dict with `status = "proposed"` (a new status). In `NOVAApp._autonomy_loop()`, before the existing `for item in goals_snapshot` loop, check for proposed goals older than 5 minutes that the user hasn't interacted with — if `settings.AUTONOMY_ENABLED` and the proposed goal's risk score is `< 4` (low risk via `guardrails.check()`), auto-approve and set status to `"pending"`. High-risk proposed goals wait for explicit approval.
- **Action**: NOVA autonomously queues goals like "Run test suite since you just committed to main" (triggered by git watcher from Tier 1) or "Fetch this week's sprint tasks from Jira" (triggered by Monday morning + `MasterMCP.connect_builtin("jira")` being active).
- **Output**: Telegram message: "I queued a goal: [goal description]. It'll run in 5 minutes unless you cancel it (`/cancel_goal goal_id`)."
- **Safeguard**: Proposed goals are only auto-approved if: `risk.score < 4`, `settings.AUTONOMY_ENABLED == True`, no `guardrails.is_emergency_stopped()`, and fewer than 3 goals are currently running. The 5-minute delay gives the user a cancellation window.
- **Competitive Edge**: Friday/JARVIS assistants execute goals on command. This synthesizes goals from observed context — no command needed. The 5-minute grace period is a UX pattern not implemented anywhere in the open-source space.

### Context Pre-Loader with Speculative RAG

- **Trigger**: `WorkContextTracker` (Tier 1) emits a context transition event — user moves from browser to terminal, or from terminal to IDE, or opens a new file type.
- **Mechanism**: Add `_speculative_prefetch(transition: str)` to `NOVAApp`. This method calls `IntentGraph.predict_next_intent()` with the transition as context, generating up to 3 predicted queries. Then fires `MemoryRouter.search(predicted_query, session_id, top_k=5)` for each on `NOVAApp._memory_executor`. Results are stored in a new `NOVAApp._prefetch_cache: dict[str, list]` (keyed by predicted query, TTL 120 seconds). In `NOVAApp._context_messages()`, before calling `self.memory.search(user_text, ...)`, check `_prefetch_cache` for entries that semantically overlap with `user_text` using a Jaccard similarity check via `HybridRanker._jaccard()` (already exists in `web/hybrid_ranker.py`). If overlap > 0.3, inject cached results as *additional* memories without an extra DB call.
- **Action**: When the user types their first question after switching context, the memory results are already in cache — RAG latency drops from 200-500ms to ~5ms for cache hits.
- **Output**: Invisible. The user just notices NOVA answers faster and with better recall.
- **Safeguard**: `_prefetch_cache` is capped at 20 entries. Cache is cleared on `reset_context()` and `switch_session()`. Only queries fired if `NetworkState.is_online()` OR ChromaDB is available locally.
- **Competitive Edge**: Speculative RAG (pre-fetching before the query is formed) is a research-level technique. No open-source assistant project implements it in a production codebase.

### Deadline and Commitment Tracker

- **Trigger**: Every `_commit_memory_async()` call scans the new conversation turn for temporal commitments using a regex pass before storing to memory.
- **Mechanism**: Add `utils/commitment_extractor.py` with `extract_commitments(text: str) -> list[Commitment]`. `Commitment` is a dataclass with `description: str`, `deadline: datetime | None`, `confidence: float`. Use a regex battery targeting patterns like: `"(by|before|on|until) (monday|friday|tomorrow|next week|\d+ (days?|hours?))"`, `"(need to|must|should|have to) .{5,60} (by|before|on)"`, `"(deadline|due|ship|deploy|release|submit) .{0,30} \d"`. Extracted commitments with `confidence > 0.6` are stored via `MemoryRouter.add()` with `metadata={"source": "commitment", "deadline_ts": ts}`. In `TaskScheduler`, register a daily 9am job that calls `MemoryRouter.search("commitment deadline", session_id, top_k=10)`, filters for items with `deadline_ts` within 48 hours, and fires `NOVAApp._notify_telegram()` with a structured reminder.
- **Action**: NOVA notices "I need to deploy the auth service by Friday" said casually on Tuesday and autonomously schedules a reminder for Thursday 9am — without being told to.
- **Output**: Thursday 9am Telegram: "Reminder: you mentioned deploying the auth service by Friday. Current status unknown — want me to check your git status or Jira?"
- **Safeguard**: Only commitments from the *user's own messages* (role `"user"` in session history) are extracted. NOVA's own responses are excluded. Maximum 20 active commitments tracked at once.
- **Competitive Edge**: Calendar integrations extract commitments from calendar events. This extracts them from *casual conversation* — where most real commitments actually happen.

### Attention-Aware Interrupt Scheduler

- **Trigger**: `NOVAApp._handle_proactive_alert()` currently fires immediately via `notify_background_event()`. New trigger: before firing, check `WorkContextTracker.current_attention_state()`.
- **Mechanism**: Add `AttentionState` enum: `DEEP_FOCUS`, `BROWSING`, `IDLE`, `IN_MEETING`, `TRANSITIONING`. `WorkContextTracker` computes this from: OmniParser UI elements (is a text editor with many lines visible = DEEP_FOCUS), process monitor (zoom/teams = IN_MEETING), screen activity delta (no mouse movement for 5 min = IDLE). In `NOVAApp._handle_proactive_alert()`, wrap the existing `notify_background_event()` call in a check: if `attention_state == DEEP_FOCUS`, add the alert to a new `NOVAApp._queued_alerts: deque` (maxlen=20) instead of firing immediately. A background timer checks every 60 seconds if the state has shifted to `IDLE` or `BROWSING` and then drains `_queued_alerts` in batch, grouping related alerts with the LLM into a digest message.
- **Action**: Instead of interrupting a developer mid-function with "I saw an error on screen", NOVA waits for a natural pause and delivers: "While you were focused, I noticed: 3 things worth your attention — [grouped digest]."
- **Output**: Batched Telegram digest during natural break points. TTS plays during IDLE only.
- **Safeguard**: `IN_MEETING` state suppresses TTS entirely (only Telegram). DEEP_FOCUS state queues but never drops alerts. Emergency/high-risk alerts bypass queueing regardless of attention state.
- **Competitive Edge**: This is the most human-centered feature in this plan. The problem of "AI assistants interrupting at the worst possible moment" is universally complained about and universally unsolved.

## PROACTIVE INTELLIGENCE TIER 4 — Autonomous Action Layer

### Preventive Maintenance Orchestrator

- **Trigger**: Daily 3am `TaskScheduler` job registered in `NOVAApp.__init__` alongside the existing `schedule_daily_backup()` call in `main.py`.
- **Mechanism**: Add `tasks/maintenance.py` with `MaintenanceOrchestrator.run_daily_maintenance(app: NOVAApp) -> dict`. It executes a fixed sequence using existing tools through `NOVAApp.goal_runner.run()`:
  1. `win32_api.disk_info` — check free space, fire alert if < 10GB
  2. Check `exports/` directory size, delete exports older than 30 days (using `win32_api.delete`)
  3. Compress `logs/jarvis.log` if > 50MB (using `win32_api.launch_process` with tar/gzip)
  4. Call `MemoryRouter.sync_all_pending()` — already exists
  5. Call `backup._backup_chromadb()` — already exists
  6. Verify `OmniParserServer.is_running()` and restart if needed — already exists in `HealthMonitor`
  All steps are run as a `GoalRunner` plan so each step goes through `guardrails.check()` — none of these should exceed risk score 4. Results are stored in a maintenance log at `.jarvis/maintenance_log.jsonl`.
- **Action**: Every morning NOVA has already cleaned up, backed up, and verified itself. The developer starts the day with a healthy system.
- **Output**: Silent if everything is healthy. Telegram message only if an anomaly was found (e.g., "Disk at 87% — I deleted 2.3GB of old exports").
- **Safeguard**: Maintenance runs only between 2-4am (check `datetime.now().hour`). All deletions go through `guardrails.check()`. The `dry_run=True` flag is used for a pre-flight pass before actual execution.
- **Competitive Edge**: Self-maintaining AI systems exist in DevOps tooling (Ansible, etc.) but not in personal AI assistants. NOVA is the first personal assistant that takes care of its own infrastructure.

### Goal Outcome Learning and Re-planning

- **Trigger**: `NOVAApp._autonomy_loop()` currently sets `item["status"] = "failed"` and stops. New trigger: on `status == "failed"` with `result.status == "stopped"` or `result.status == "failed"`.
- **Mechanism**: Add `_handle_goal_failure(goal: dict, result: GoalResult)` to `NOVAApp`. When a goal fails, this method:
  1. Extracts the failing step: `steps[result.next_index]`
  2. Calls `LLMEngine.ask()` with prompt: `"This goal step failed: [step]. Error: [result.reason]. Suggest ONE alternative approach using available tools: [dispatcher.get_tool_schema_prompt()]"` — the alternative is parsed as a new step dict
  3. If alternative step passes `guardrails.check()` with score <= 6, insert it into `goal["steps"]` at `result.next_index` and set `goal["status"] = "pending"` for one automatic retry
  4. Second consecutive failure on the same goal → mark as `"requires_human"`, notify via Telegram with a specific question: "Goal X is stuck on step Y. I tried Z. Want me to try [alternative] instead?"
- **Action**: Goals become self-healing. A web scrape that fails because a site blocked the request automatically retries with a different URL strategy.
- **Output**: Silent on first auto-retry. Explicit Telegram consultation on second failure.
- **Safeguard**: Maximum 2 automatic replanning attempts per goal (tracked in `goal["replan_count"]`). Re-planned steps still run through the full `guardrails.check()` + `authorize()` pipeline.
- **Competitive Edge**: AutoGen has retry mechanisms but they are fixed-strategy (same approach, different input). This generates *novel alternative approaches* using the full tool schema as context — genuine adaptive replanning.

### Proactive Documentation and Knowledge Capture

- **Trigger**: `GoalRunner.run()` returns `status == "completed"` for any goal with more than 3 steps. Also triggered when `FileSystemEventHandler` (Tier 1) detects a new `.py`, `.md`, or `.txt` file created in a project directory.

### Multi-Channel Presence Manager

- **Competitive Edge**: No personal assistant routes notifications based on context and channel availability. This transforms NOVA from "a Telegram bot" into a presence that follows the developer across their entire digital workspace.

## PROACTIVE INTELLIGENCE TIER 5 — Self-Evolution Layer

### Tool Performance Profiler and Optimizer

- **Trigger**: Every `guardrails.log()` call in `safety/guardrails.py` — currently writes a JSONL line with `tool`, `status`, `risk_score`. This is the perfect existing hook.
- **Mechanism**: Add `utils/tool_profiler.py` with `ToolProfiler`. It reads `logs/guardrails_actions.jsonl` on startup and builds a `dict[str, ToolStats]` where `ToolStats` has `success_rate: float`, `avg_latency_ms: float`, `failure_reasons: Counter`. `ToolProfiler.get_reliability_ranking() -> list[tuple[str, float]]` returns tools sorted by success rate. In `Dispatcher.get_tool_schema_prompt()`, add an optional `reliability_hints: dict` parameter — when provided, append to each tool's schema description: `"(reliability: 94%, avg 120ms)"`. Call this from `build_system_prompt()` in `core/think/reasoning.py`. Additionally, in `_plan_goal()` in `NOVAApp`, inject the top-3 least reliable tools as a warning into the planner system prompt: "These tools have had recent failures: [list]. Prefer alternatives when possible."
- **Action**: The LLM planner learns to avoid flaky tools and prefer reliable ones. Goal plans become more robust over time without any explicit retraining.
- **Output**: Exposed via a new `tool.stats` registered tool in `NOVAApp._register_builtin_tools()`.
- **Safeguard**: `ToolProfiler` only reads from the JSONL log — never modifies `Dispatcher` registrations. Reliability hints are purely advisory to the LLM.
- **Competitive Edge**: No open-source agent framework feeds tool reliability statistics back into the planning prompt. This closes the feedback loop that every agentic system currently leaves open.

### Goal Template Library Builder

- **Trigger**: `NOVAApp._autonomy_loop()` when `status == "completed"` for goals that took more than 3 steps and completed without replanning.
- **Mechanism**: Add `core/goals/template_library.py` with `GoalTemplateLibrary`. On successful goal completion, extract a generalized template from the goal's step sequence: replace specific values (URLs, filenames, dates) with typed placeholders using a regex pass (`https://[^\s]+` → `{url}`, `/home/user/[^\s]+` → `{filepath}`). Store the template as: `{"name": inferred_name, "trigger_keywords": extracted_nouns, "steps": generalized_steps, "success_count": 1, "avg_completion_time": t}` in `.jarvis/goal_templates.json`. `GoalTemplateLibrary.find_matching_template(goal: str) -> Template | None` uses `HybridRanker` (already exists in `web/hybrid_ranker.py`) to find the closest template by `trigger_keywords` similarity. In `NOVAApp._plan_goal()`, before calling `LLMEngine.ask()` for planning, call `template_library.find_matching_template(goal)` — if match score > 0.7, use the template directly, skipping the LLM planning call entirely.
- **Action**: The second time NOVA is asked to "fetch and summarize today's GitHub PRs and post to Slack", it uses the template from the first time — instant planning, no LLM call, lower cost, higher reliability.
- **Output**: Silent. Optionally surfaced: "I used a template from a previous goal — planning took 0ms."
- **Safeguard**: Templates are only used if the new goal's dispatcher tool registry still contains all required tools. A stale template with a removed tool is automatically invalidated.
- **Competitive Edge**: AutoGen has no persistent goal template learning. LangGraph has workflow definitions but they're hand-coded. This is emergent workflow discovery from successful execution history.

### Automatic Plugin Synthesis from Repeated Patterns

- **Trigger**: `ToolProfiler` (new, above) detects that the same sequence of 3+ tools has been called in the same order at least 8 times across different goals (tracked in a new `call_sequence_counter: Counter` on `ToolProfiler`).
- **Mechanism**: `ToolProfiler.detect_combinable_sequences() -> list[ToolSequence]` runs after every 50 tool calls (a counter on `Dispatcher`). When a sequence is found, it calls `PluginGenerator.generate_and_propose()` (already exists in `core/plugin_generator.py`) with a description constructed from the sequence: `"A tool that combines web.search, web.scrape, and doc.ingest into a single operation: search for [topic], scrape the top result, and add it to the knowledge base."` The existing human approval gate in `PluginGenerator._cli_confirm()` applies — NOVA proposes, human approves.
- **Action**: NOVA notices "every time I do research, I search → scrape → ingest" and proposes a single `research.add_to_knowledge_base` tool that does all three with one call.
- **Output**: Telegram message: "I noticed you've done [search→scrape→ingest] 9 times. I wrote a plugin that combines these — want me to install it? [view code link]"
- **Safeguard**: The existing dual-gate in `PluginGenerator` (AST check + human approval) is never bypassed. Proposed plugins are written to `.jarvis/pending_plugins/` and require explicit `/approve_plugin` command.
- **Competitive Edge**: This is the only open-source system where the assistant observes its own tool usage patterns and proposes architectural improvements to itself. It's genuine meta-cognitive behavior.

### Feedback-Driven System Prompt Evolution

- **Trigger**: Weekly cross-session insight extraction (Tier 2) completes AND at least 10 goals have been executed since the last evolution cycle.
- **Mechanism**: Add `core/think/prompt_evolver.py` with `PromptEvolver`. It maintains a `prompt_variants.json` file with A/B test records: `{variant_id: {prompt_suffix: str, goals_run: int, success_rate: float, avg_steps: float}}`. When a new weekly insight is generated, `PromptEvolver.propose_variant(insight: str)` calls `LLMEngine.ask()` with: `"Based on this user insight: [insight], suggest ONE short addition (< 50 words) to this system prompt that would make NOVA more proactively helpful: [current_system_prompt]."` The proposed addition is stored as `variant["candidate"]`. In `NOVAApp.ask_stream()`, 20% of calls use the candidate variant (selected via `hash(session_id + str(date.today())) % 5 == 0`). `PromptEvolver.evaluate_variant()` runs after 20 goals to compare success rates. If the variant improves success rate by > 5%, it graduates to become the new `SOUL.md` tail section.
- **Action**: NOVA's personality and working style subtly improve based on what has actually worked — not what was hardcoded at install time.
- **Output**: After a variant graduates: Telegram message: "I've updated my working style based on what's been working best. You can review the change in SOUL.md."
- **Safeguard**: A/B testing is strictly session-local (determined by session ID hash, not random, so it's reproducible). Variants that decrease success rate by > 10% are immediately retired. Maximum one A/B test active at any time.
- **Competitive Edge**: No personal AI assistant performs self-directed prompt engineering based on its own outcome data. This makes NOVA a genuinely self-improving system within strict, auditable bounds.
